# ADR-008: NPM Release Strategy & Automated Pipeline

**Status:** Accepted  
**Date:** 2026-10-03  
**Deciders:** Principal Architect, DevOps & Release Engineering

---

## 1. Context and Problem Statement

Manual npm package publishing from individual developer machines is error-prone, untraceable, and a frequent cause of supply chain vulnerabilities and compromised npm credentials.

A production-grade open-source component library must implement an immutable, auditable, fully automated release pipeline.

---

## 2. Decision

1. **Automated Publishing via GitHub Actions:**
   - All production package publishing must occur strictly within GitHub Actions CI/CD workflows.
   - Manual `npm publish` executed from local developer workstations is **strictly prohibited**.
2. **NPM Build Provenance (OIDC):**
   - Publish with `--provenance` via GitHub Actions OpenID Connect (OIDC).
   - Generates verifiable cryptographic attestations linking published npm packages directly to the exact Git commit and build runner.
3. **Changesets Orchestration:**
   - Releases are initiated by merging an automated "Version Packages" pull request generated by `@changesets/cli`.
   - Merging this PR triggers `pnpm changeset publish`.
4. **Automated Git Tagging & GitHub Releases:**
   - Git tags (`@chellaa/react@<version>`) and GitHub Releases are created automatically upon successful npm publishing.
5. **Dry-Run Tarball Inspection Gate:**
   - Every release job must run `npm pack --dry-run` and inspect the tarball inventory prior to publishing.

---

## 3. Consequences

### Positive

- **Supply Chain Security:** Consumers can verify cryptographic provenance on npm.
- **Auditability:** Every release maps directly to a merged PR and Git commit.
- **Consistency:** Changelogs, Git tags, GitHub releases, and npm versions are updated in lockstep.

### Negative

- **Requires OIDC Token Configuration:** Requires npm organization permissions configured for GitHub Actions OIDC trust.

---

## 4. Alternatives Considered

1. **Local Publishing by Core Maintainers:** Formally rejected due to security risks and lack of provenance.
2. **Semantic-Release:** Rejected in favor of Changesets due to Changesets' superior monorepo support and decentralized PR changelog workflow.
